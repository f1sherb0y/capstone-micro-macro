# e2e-case0014-1119：真实模型端到端跑通（CASE-0014）

2026-11-19 运行。状态：**跑通，待验收**。模型 `deepseek-flash`；微观多岗位讨论（`multi`）；宏观为 GBA 规则引擎。

项目：氹仔污水厂排放管改道及周边平整工程（澳门，DBB）。情景总预算 MOP 1.5 亿，工期 24 个月。

## 流程

业主组织用模型讨论拆包 → 每个包依次走需求细化、企业投标决策、投标文件、开标、评标、定标、多方签约（最多三稿）→ 合同写入宏观 → 宏观按时间步推进设计、施工、付款、检查和结算 → 项目关闭。42 个时间步，模型调用 498 次，输入约 375 万 tokens，输出约 28 万 tokens。完整数字见 [SUMMARY.md](SUMMARY.md)。

### 合理性判断

- 6 个包都一轮完成采购，合同价都在包预算之内。施工包有 3 家竞争，报价相差不到 0.6%。
- 施工包 1 没有选最低价（COMP-0494 报 6012 万），选了报价 6046 万、单列 438 万风险准备金的 COMP-0153，理由是报价基础透明、技术方案覆盖全部范围。
- 签约谈判有实质内容。施工包 1 第一稿双方都要求修订，争点是停水接驳窗口和试压验收标准未确认时的工期责任。业主第二稿要求承包商不得顺延，承包商拒绝并给出替代条款；第三稿写入“业主应于合同生效后 28 日内书面确认，逾期则里程碑顺延，待命费用在风险准备金内据实结算”，双方接受。
- 需要留意：设计包和施工包 1 的材料包报价几乎等于预算上限；6 个包全部用满三稿才签约，说明签约环节仍偏保守。成本超出总预算 3.5% 来自宏观规则引擎的执行阶段，不是签约价超支。

## 为跑通所做的修改

此前同一案例在第 4 步停止：设计、造价两个包三轮都签不了约。原因和修改如下，均为默认关闭的开关，由 `scripts/run_e2e_case.py` 打开，不改变已冻结实验的行为。

| 卡点 | 原因 | 修改 |
|---|---|---|
| 投标人一份标都递不出 | 讨论中提出的“递交前须核实”事项没有任何人能核实，永远阻塞递交 | 内部核验台 `src/condition_review.py`：只依据该企业被授权看到的情景资料逐条回答；资料能证实的记为已核实，资料没有的由管理层决定作为公开假设继续投标或退出；从不编造文件 |
| 签约三稿都是“修订” | 业主要求的是它自己的书面立场，却每稿都等这份立场 | `integration/sessions.py`：告知各方哪些问题由自己决定、第三稿是终稿；业主起草修订稿时必须直接写明自己的决定 |
| 签约回答格式不合规 | 模型把条款放在额外字段里 | 明确只能有 action 和 reason 两个字段 |
| 投标文件因报价分项不闭合被丢弃 | 只允许重写一次，且模型看不到自己的错误答案 | 定向修正 `AgentRuntime.targeted_repair_retries`：把被拒答案和校验信息一起返回，最多再改三次；主机不改任何数字 |
| 材料包无人投标 | 材料包范围照抄施工包全文，供应商读成施工包而放弃 | `integration/planning.py`：材料包范围写明只供货、不含施工 |
