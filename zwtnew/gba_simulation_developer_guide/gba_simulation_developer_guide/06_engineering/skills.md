# 技能能力与接入规范

规范性质：技能方法、候选能力与平台接入要求。能力定义、实际技能制品、运行接入和行为验证分别登记；没有注册、调用与校验证据的能力保持未接入。

[总入口](../README.md) · [角色目录](../README.md) · [项目流程](../03_projects/project_lifecycle.md) · [政策量化](../05_policy/quantification.md) · [整次运行](../07_experiments/run_and_results.md)

平台适合建立可复用的 AI 技能层。政策解读、方案比较、资料审查、变更影响分析等任务，需要稳定的专业方法和结构化输出；计算、权限和正式状态则由有明确契约的工具与核心维护。技能粒度按可独立复用和验证的任务确定，不按角色数、流程节点数或文档数量决定。

## 1. 角色、流程、技能与工具的职责

| 层次 | 核心问题 | 本项目中的例子 |
|---|---|---|
| 角色与实例 | 谁行动、追求什么、知道什么、拥有什么权限和资源？ | 有独立认知和现金的 Owner；有事项权限的 Government |
| 业务流程 | 哪个事项何时能启动，由谁承担，需要哪些输入和接受，失败后怎么办？ | 提案→专业评估→投资；采购轮次、工作依赖与交接 |
| AI 技能 Skill | 如何完成一项分析、编制、审查或受限选择任务？ | 提取政策条件、比较供货方案、分析改图影响 |
| 工具与仿真核心 | 如何查询/计算，并依法定或模型权限校验和提交实际变化？ | 资格匹配、计价、排程、账本、任务提交及事件投递 |

**SKL-001｜技能是可复用的方法包。** 包含触发条件、输入要求、任务方法、可调用工具、输出契约和能力边界，可以配套参考资料、模板与代码工具。角色提供身份、目的和偏好，流程提供任务与条件；技能既不是新的企业，也不持有另一份正式项目状态。

例如供应商用“供货方案比较”技能形成可选批次与报价，是否接单取决于自己的商业判断；产能计算工具报告已知窗口约束，核心在提交承诺时再次核验。供应商认为自己能交货、系统接受了合同和货物实际到达，是三个不同事实。

## 2. 助手侧与仿真平台侧的使用环境

**SKL-002｜开发助手使用技能，与平台角色调用技能，是两条接入链。**

- **研究/开发助手侧**：帮助整理政策、写规范、检查文档、设计实验和审阅结果。项目文件中的 `SKILL.md` 可作为有明确来源的方法说明；是否被宿主自动发现另按其技能机制配置。
- **仿真平台侧**：平台角色在运行中调用有版本的能力，需要实现技能注册、任务匹配、上下文构建、工具权限、结构化输出、失败处理和调用记录。仅把文件命名为 `SKILL.md` 不会让平台自动执行。

方法可以共享，访问范围不能自动共享。研究准备可以查看获授权的政策全集和全局数据；运行内 Owner、Bank 等只读取自己的可见资料。结果分析可以审计隐藏真值，不能把这些结果反向注入当时角色的判断。

本章维护平台的技能边界和候选能力图，不规定某一模型厂商的自动加载方式，也不要求所有技能同时装入每次决策上下文。

## 3. 政策建模能力

政策建模能力覆盖原文来源、条款拆解、字段抽取、证据画像、宏观/混合/原子路径、机制映射、参数依据与情景建议。证据结构化只回答原文写明了什么、哪些内容仍不确定；效果估计需要独立数据、方法和运行结果。以下契约足以定义能力边界，不要求读者取得包外技能文件。

**SKL-003｜政策建模能力按任务分模块。** 候选入口名为 `policy-modeling`，支持 [政策量化](../05_policy/quantification.md) 的完整六步；具体制品名和装配方式登记在能力清单中。下表定义模块职责，不代表技能已创建或接入。

| 任务模块 | 输入 | 输出 | 依赖的程序工具 |
|---|---|---|---|
| 证据结构化 | 原文/版本/来源、事项与大湾区范围 | 条款、逐字段依据、缺口与路线建议 | 原文定位、资料读取、单位/引用检查 |
| 机制与工具映射 | 条款、[工具目录](../05_policy/instrument_catalog.md) 的工具目录、支持范围 | 作用对象、触发、直接改变、角色响应、依赖/冲突候选 | 工具目录检索、配置支持查询、规则引用检查 |
| 参数依据整理 | 明文数值、观测资料、方法、显式假设 | 类型/单位/基数、来源、方法引用、不确定性与待核项 | 数值换算、估计/校准程序、参数 schema 校验 |
| 情景设计与解释 | 研究问题、候选工具、预算/能力、比较口径 | 基准、单项/组合/消融/压力情景建议及可行性说明 | 组合依赖/覆盖检查、配置生成与版本比较 |

技能可解释政策并提出机制/参数候选；它不能从模糊措辞直接生成经过验证的效果系数。真实参数估计交给有数据和方法的工具，缺失则保留未知或明确的情景假设。情景“强”不保证结果更好，数值预算也不代表实际现金。

证据输出遵守 POL-002：数值目标、规则、对象、时间、资源分别记录明确／部分／缺失／不适用及依据，来源真实性、提取把握和核验状态另列。未经校准的综合小数不得充当政策力度、效果系数或自动通过门槛；候选技能中的示例值不能进入正式情景默认配置。

典型运行链：研究者给出政策材料和研究问题 → 技能整理依据、机制与情景建议 → 程序核对类型/单位/依赖/覆盖 → 选定并冻结场景 → 仿真按时序应用规则 → 角色独立响应 → 正式执行 → 分析实际结果。内生 Government 政策调控仍依 D-08，不因有政策技能就自动开启。

## 4. 候选能力与角色使用范围

先按使用场合组织能力，而不立即创建大量目录。以下均为候选设计；同类方法可以跨角色复用，实际输入、目标、资格和权限由调用者限定。

| 使用场合 | 建议能力 | 典型交付物 |
|---|---|---|
| 研究准备 | 政策建模 | 来源明确的条款、机制、参数与情景建议 |
| 研究准备 | 数据解释与初态检查 | 字段对应/实体匹配候选、缺口、期初差异；合并/补全按明确方法另行执行 |
| 运行内 | 需求简报编制 | 目的、候选地区、规模/交期、约束与调查问题 |
| 运行内 | 多方案比较 | 同口径方案、证据和不确定性、按本主体目标的取舍理由 |
| 运行内 | 委任/采购资料审查 | 同版成果/报价/条件的差异、缺项、澄清问题 |
| 运行内 | 专业方法选择与结果解释 | 支持方法、所需输入、有限范围意见；不替代工程计算或真实检验 |
| 运行内 | 变更影响分析 | 受影响成果/许可/采购/工作/资金、待确认接口和可继续范围 |
| 运行内 | 协商与受限选择 | 有来源的条件建议，或契约明确要求的接受/拒绝/延期决定 |
| 运行内 | 履约与异常接续分析 | 分批/改期/替代/整改候选及后果；不直接变更他方承诺 |
| 研究评价 | 实验设计与结果解释 | 对比设计、作用证据、失败/未完样本、主张与验证限制 |
| 开发维护 | 契约与闭环审查 | 跨文档/接口缺口、独立预期、影响范围；不计作仿真企业行为 |

**SKL-004｜八角色共享方法，不共享目标或认知。** 每个角色可以有多个技能，一个技能也可被多个角色复用；不需要“一个角色一个总技能”才算完整。

| 角色 | 可用技能的代表任务 | 工具/核心继续维护的事实 |
|---|---|---|
| Owner | 形成简报、比较专业方案、判断投资/延期、分析变更 | 真实现金、有效授权、投资/委任提交及需求存量 |
| Bank | 审查资料、识别支用条件、形成授信/补救选择 | 本金/利息、额度/资金占用、实际提款和清偿 |
| Architect | 需求转译、候选方案、接口协调、修订说明 | 有版本的专业计算、实际工作投入、成果发布与允许用途 |
| Engineer | 编制受托专业方案、选择适用检查、解释结果、形成限定意见 | 支持方法计算、实际试验/检查证据、输入与范围校验 |
| QS | 量价范围核对、比较报价、计量/变更审阅 | 数量计算、金额/币种/税费口径、核证增量与账本 |
| Government | 事项分流、资料审查、形成权限内案件决定 | 事项权限、生效与时钟、必要条件、许可提交及监管事实 |
| Contractor | 投标取舍、工作安排、变更/停复工方案、交付资料汇集 | 实际产出、材料消耗、投入/成本、排期占用和交付状态 |
| Supplier | 产品匹配、报价/接单、批次/路线选择、退换接续 | 库存、制造/物流计算、实物位置、实际接收与付款 |

这里的“判断”可以涉及商业报价、风险偏好和专业意见，不要求把所有选择改成确定性评分。正式工程真值、真实资金和资源状态则保持共同规则；同样的工具结果也可以使不同主体作出不同选择。

工程类技能读取 [工程模板](../02_world/project_types.md)及其绑定的设计变量与方法引用，按工程对象、任务、输入和权限匹配能力。建筑方案技能不能自动处理道路／桥梁；Engineer 的方案编制和独立检查是不同职能。超出适用域、缺少方法或必要资料时返回明确结果，不因语言模型能描述一种工法就登记为可运行模板，也不因新增工程目录自动新增技能或角色。

## 5. 调用、输出与副作用协议

**SKL-005｜先绑定任务和身份，再提供技能上下文。**

```mermaid
flowchart LR
    T[业务事件与有权任务] --> C[主体身份、目标、可见证据]
    C --> S[选取支持该任务的技能版本]
    S --> R[按权限查询或调用计算工具]
    R --> O[建议、专业成果或显式决定]
    O --> H[宿主绑定原任务与稳定命令身份]
    H --> V[当前状态、权限、候选与资源校验]
    V --> E[核心提交正式事件]
    E --> F[有限观察与后续待办]
```

上图是默认的宿主提交模式。技能匹配先检查任务类型、适用范围和可用工具，再按需加载材料；复杂任务可以分解，普通任务不必额外套一层总路由。技能调用和模型对话不增加业务施工时间，实际工作持续时间由对应任务方法决定。

**SKL-006｜输出有明确业务效力。** 返回结构区分 `proposal`、`professional_artifact`、`decision` 以及 `needs_information`、`unsupported`、`technical_error` 等结果。它们是语义类别，具体字段按对应动作契约定义。

传输边界采用[共用输入输出协议](interface_contracts.md)：ActionResult的completed只说明类型化材料或选择已形成，Payload再按该动作区分建议/成果/决定及choice；提交效果只能来自核心回执。每个Skill绑定角色Input/Payload或系统方法schema，不能把上述语义类别另建成与ActionResult冲突的一套状态；host_submit技能与方法工具返回MethodResult，查询工具返回QueryResult。managed_steps使用系统接口的skills.execute_managed及ManagedSkillAttemptResult，不能套用纯材料返回体丢掉已提交/未决步骤；公共外部执行状态见[输入输出协议](interface_contracts.md#52-共用核心函数)。

建议不能被自动提升为接受；若任务明确授权本主体作最终选择，技能可以产出显式 Decision，但仍由核心校验并提交。接收专业意见这一事实不证明意见内容必然正确；采用范围、商业接受与法定许可仍分开。原状态改变时重新核验，不沿用过期工具结果。

每次平台任务先经core.register_invocation登记DecisionTask/SystemTask/WorkspaceTask及稳定调用身份，再登记 `task_run_id`、主体/职能、动作契约、对象/上下文版本、技能/工具版本和 `execution_mode`，在首次调用前持久化。默认 `host_submit`：Skill 只读取/计算并返回允许类型；宿主将已登记的最终 Decision 绑定原任务及稳定 `command_id`，交 [开发契约](implementation_contracts.md) 第 7 节的唯一提交入口，不再请另一个 LLM 重复决定。建议/材料若需发布，也走其自身获授权的发布动作，不能借此变成接受。宿主不替主体改变决定内容或扩大允许动作。

技术重试可有不同 `attempt_id`，但不另造同一业务任务/命令。宿主保存采用的最终返回与摘要，同任务的不同尝试不能各自提交一个结果；返回冲突须按原任务状态处理，已经提交后只能引用原结果，不能用迟到返回覆盖。新业务选择或对象修订使用有父引用的新任务/版本，并重新满足对应门控。

**SKL-007｜技能中的工具分访问类别。**

| 类别 | 可做的事 | 提交边界 |
|---|---|---|
| 查询工具 | 按身份读取证据、候选及可见资源视图 | 保留读取范围和版本，不暴露隐藏真值 |
| 分析/计算工具 | 单位换算、方案估算、支持的工程检查、情景试算 | 返回带方法/输入引用的结果；试算不修改正式世界 |
| 命令工具 | 依动作契约申请、提出报价、提交接受或执行请求 | 默认由宿主执行器调用；只有显式登记的多步模式向 Skill 开放。均经核心校验，不直写领域状态 |

工具用何种技术实现与其业务效力是两个问题。规则/计算可确定或含受控随机性；技能也可以直接引用固定程序。禁止以“工具调用成功”代替“正式事实已提交”，并依 OBJ-012 处理已提交、未提交、结果未知及迟到核对。

确有连续副作用需求时，任务契约可选择 `managed_steps`，不因 Skill 自称需要就启用。宿主按获授权的步骤/工具范围持久管理逻辑 `step_key`、输入版本和稳定子命令身份；同一步技术重试复用身份，合法的新步骤/修订另登记关系。每步独立校验并记录回执，最终返回ManagedSkillReport，保留逐步CommandAttemptResult、已提交引用、未决步骤和终止原因；无法取得可信完整报告时返回unknown并查询原invocation，不能回退为零副作用的MethodResult.technical_error；其中已执行决定不能再当新命令提交。步骤先后依本任务契约，不由 Skill 任意跳过前置条件。

任务技术结果与子命令业务结果分别保存：后续超时/拒绝不撤销前面合法提交，结果未知先查原执行；需要撤回、补偿或退款时另用已有权限下的正式动作，不能“重跑整个技能”抹去事实。默认模式拒绝 Skill 直接调用命令工具；两种模式在装配时确定，同一任务中不能静默切换。类型、稳定身份与返回分支的唯一技术主定义在[公共接口协议](interface_contracts.md)；提交拥有者、事务及恢复职责在[软件架构 第7节](implementation_contracts.md#7-软件实现映射)，此处只规定技能调用模式。

## 6. 技能包契约

**SKL-008｜技能包只保存可复用方法和必要资源。** 真正创建时以清楚的名称/描述说明何时使用，正文保留必要流程和边界；较长的参考、输出格式和算例按需另存。业务主规则仍在对应领域规范，避免复制后各自漂移。

| 契约面 | 要定义什么 |
|---|---|
| 身份/版本 | 技能 ID/版本及内容摘要、引用的动作/schema/方法/工具/提示版本和兼容关系、支持状态与不适用范围 |
| 使用场合 | 研究准备、运行内或开发评价；谁可以调用，什么任务触发 |
| 输入 | 主体/授权/目标、对象与候选版本、证据来源、信息截止、未知及缺项语义 |
| 工作方法 | 必要判断步骤、可变选择空间、应查依据与工具；不要求所有任务同一种模板答案 |
| 工具与权限 | `host_submit` 或 `managed_steps`、真实可用工具及查询/试算/命令类别、允许步骤/必要输入和实际副作用 |
| 输出 | 建议/成果/决定的类型、字段、证据引用、不确定性及失败/拒绝分支 |
| 调用预算 | 既有授权下的调用次数/耗费上限、终止与续办规则；不自动购买或扩大预算 |
| 隔离与记录 | 运行/主体/任务/尝试命名空间、逻辑步骤及命令身份、上下文/工具结果引用、采用的返回、提交/未决结果 |
| 验证 | 正常、缺项、陈旧版本、越权、工具失败/未知等案例；方法正确性与现实有效性分开 |

**SKL-009｜共享技能保持主体独立。** 两个银行使用同一审查方法，不共享私有风险判断和记忆；两个供应商可以选择不同利润与排期。共享的只有静态方法或明确允许共享的公共资料。缓存/记忆包含运行、主体、技能/动作、输入版本和可见信息范围；技能不能读取研究者的全局审计视图替主体作全知判断。

装配时固定上述技能内容与兼容依赖；同版本名但内容不同按不同制品处理，不能在续办时静默换用。缓存的分析/决定结果不包含可重新执行的正式副作用；拿到缓存命令回执只能查询原提交，仍受当前任务身份/模式约束。共享公共方法缓存也必须匹配输入与可见范围，不能借命中缓存绕过权限。观察消费和认知变化按 [开发契约](implementation_contracts.md) 的同次保存/排重规则接入，不能因重新收到事件又学习一次。

**SKL-010｜失败不偷偷改变商业含义。** 无可用工具、模型故障或预算不足返回明确技术结果；缺事实返回待补信息；不支持方法返回不支持。业务上的拒绝/不行动由角色合法选择产生。可按已有契约重试或处理独立事项，不静默更换模型、提供者或规则替身，也不要求一次局部失败停止整个平台。

## 7. 能力选择与试点条件

建议按复用价值和可验证性推进，而不一次创建全部候选。

1. **政策建模**：按 [政策量化](../05_policy/quantification.md)/[工具目录](../05_policy/instrument_catalog.md) 贯通条款→机制→参数依据→情景建议；使用合成验收例检查输出质量和缺项处理，现实来源另行核验。
2. **方案比较**：选择一个按工程模板绑定专业职责的明确任务，由 Owner 与相关编制、核验和造价主体按各自目标比较同口径方案；所需工程方法依 D-06/07，不能用技能弥补空计算，也不强制所有项目委任同一角色组合。
3. **变更影响分析**：沿已有依赖查受影响范围和有权接续方，检验版本变化、保留已发生事实及独立工作可继续。

随后从实际重复任务中拆出资料审查、供货/排程建议、协商和研究评价能力。若一个方法只有一次用途，先保留在动作规范即可；若有独立输入/输出、反复使用和可核对行为，再形成独立技能入口。无需把每个小步骤都建成一个目录。

## 8. 实现映射与支持登记

本章维护技能体系及任务模式；角色文档维护谁能做什么及业务后果；[政策量化](../05_policy/quantification.md)/[工具目录](../05_policy/instrument_catalog.md) 维护政策方法与工具语义；[开发契约](implementation_contracts.md) 维护开发职责与提交/恢复架构；[公共接口协议](interface_contracts.md)维护类型和结果， [系统接口](system_interfaces.md#9-可见信息候选认知与技能宿主)维护具名调用签名。将来创建实际技能时，`SKILL.md` 是其中的方法入口，配套的类型/工具/加载与执行代码让它进入平台。

每项启用能力必须建立映射：`角色动作/准备任务 → 技能版本 → 可见输入 → 工具版本 → 输出类型 → 核心校验/提交入口 → 检查案例`。通用文本改动可能改变建议和选择，但新增正式状态、计算方法或工具权限仍需对应实现。每次实验固定所用技能版本，不能用更新后的技能重新解释旧决定并冒充原运行。

| 支持登记项 | 判定依据 | 无证据时的状态 |
|---|---|---|
| 方法定义 | 对应主规则、输入/输出、能力边界和验收预期 | 未定义或候选能力 |
| 技能制品 | 稳定 ID/版本、内容摘要、依赖与兼容关系 | 未登记制品，不引用机器私有路径作为可用证明 |
| 平台接入 | 注册/匹配、上下文隔离、权限和调用链 | 未接入，不因文件存在标为可调用 |
| 正式执行 | 宿主模式、稳定命令身份、校验/提交与未知恢复证据 | 未验证，试算结果不代替正式提交 |
| 行为效果 | [运行结果](../07_experiments/run_and_results.md) 的共同输入基线、预算/失败与独立评价 | 待行为验证，不把合法结构输出等同有效判断 |

## 9. 技能接入验收条件

| 检查 | 确定预期 |
|---|---|
| CHECK-SKL-001 | 输入“鼓励合作”但无数值依据：给出方向/机制候选与缺口，不编参与增长或补贴比例 |
| CHECK-SKL-002 | 同一政策有明文期限和未知处理能力：分别输出规则值与缺口，不以期限作为实际完成时间 |
| CHECK-SKL-003 | 两家银行共用技能：各自目标、资料和记忆隔离，不读到另一家私有报价 |
| CHECK-SKL-004 | 任务只要求比较方案：结果为建议/材料，不直接变成投资或委任 |
| CHECK-SKL-005 | 默认模式中有权主体被请求作最终选择：可返回契约内决定，由宿主绑定稳定命令身份提交；不新增 LLM 批准。Skill 尝试直接调用命令工具时拒绝该调用，正式状态不变 |
| CHECK-SKL-006 | 工具试算成功，但正式资源随后被占用：不能提交旧方案承诺，返回合法冲突/续办 |
| CHECK-SKL-007 | 缺工具/模型失败/预算耗尽：技术结果与业务拒绝分开，不隐式切换替身。多步模式中先提交后失败，报告已提交与未决步骤；失败不抹去承诺，也不重跑已完成步骤 |
| CHECK-SKL-008 | 工程方法不支持某方案：保留不支持/需补查，不由语言模型声明验证通过 |
| CHECK-SKL-009 | 同一命令回执重放、提交成功后最终回复丢失、多步报告再次返回同一接受：均引用原命令/子命令核对，不重复现金、合同、工程量或认知消费；同 ID 改内容报冲突，不兼容技能/工具版本在依赖入口拒绝装配 |
| CHECK-SKL-010 | 修改技能文件但平台尚无对应加载/调用链：状态仍为未接入，不宣称平台行为已改变 |

验收记录应包含技能内容摘要、依赖工具版本、输入与可见范围、实际调用方式、返回/回执和结果位置。文档、加载、调用、正式提交及行为评估是不同证据；只有相应证据齐全，才能将对应能力标为已接入或已验证。
