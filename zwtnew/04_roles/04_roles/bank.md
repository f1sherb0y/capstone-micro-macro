## 1. 职责、目标与权限

### 1.1 主体身份与授权

Bank 是在选定融资模型中提供信用或资金服务的组织角色。银行的目标可以包括风险调整收益、组合稳健、流动性、客户关系及有来源的政策任务；权重与约束应是明确模型假设或校准输入。

| 项目 | 必须表达的内容 |
|---|---|
| 身份 | 独立 `agent_id`、组织/授权业务单位、注册地、经营/服务地区、权限、数据来源和认知；借款人与项目地另列 |
| 服务范围 | 可接受的借款主体、地区、项目、用途、币种和融资产品；暂未建模的产品不自动支持 |
| 决策权限 | 谁能审查、批准、报价、调整条款、同意提款和处置违约 |
| 组合约束 | 已承诺未提款、在途执行、已提款债权、集中度及必要的资金执行能力 |
| 信息约束 | 本行记录、获授权披露、公开事实及可见核证；不拥有所有企业真实余额和私有判断 |

**BANK-001**：银行的组织资源、授信决策能力、融资承诺边界、实际资金执行能力是不同约束。不能把抽象能力评分直接当成可反复花用的资金。

**BANK-002**：基础财务模型包含现金、应收应付、贷款和到期义务的最小资金账本。D-02 仍需确定账户结构、产品、费用和执行细节；该范围不意味着已经模拟完整银行资本监管、存款创造或跨行清算，也不把任何单一现金守恒假设当作完整银行机制。

### 1.2 独立判断与经营取舍

| 自身考虑 | 决策中可比较的后果 | 必须单独检查的约束 |
|---|---|---|
| 收益与风险 | 条款下可能收入、损失暴露、审查与服务成本 | 实际可执行承诺、证据要求及授权；预期收益不是已实现利润 |
| 组合稳健 | 客户、地区、用途、产品之间的共同风险 | 集中度口径及适用限制；多项目不能各自忽略同一风险来源 |
| 资金和服务连续性 | 在途支付、提款请求、现有客户服务与新申请的资源竞争 | 资金执行能力与审查人员分别约束，不相互折算成无限容量 |
| 客户及政策任务 | 长期关系、职责内服务目标、有来源的适用政策 | 政策资格、用途和责任边界，不自动获得补偿、担保或免除风险 |

**BANK-021｜银行保留独立选择。** 政策鼓励某地区或建造方式，可以改变本行获准采用的产品条件、预期或策略；只在政策证据或明确情景规则覆盖时生效。不能据“支持建设”直接生成贷款、替业主补资金缺口，或把更多放贷设为必须达到的成功条件。

评估目标可并列记录，具体权重、风险度量、约束阈值和策略更新机制待定；不预设利率公式或完整监管资本算法。
银行可以少放贷、保留能力、补充调查或退出新业务竞争；已承担的合法承诺仍按其条款处理。

银行同时管理申请、承诺、执行中交易和存续债权，不随单个项目阶段切换停止经营。其他组织作为借款人时，仍须明确自身借款授权与接口。

## 2. 信息、状态与业务对象

### 2.1 可见信息与权限边界

| 对象 | 保存什么 | 不能混成什么 |
|---|---|---|
| 申请与审查档案 | 借款主体、项目/用途、材料版本、来源、缺项、风险判断 | 已批准贷款 |
| 内部批准与对外报价 | 权限、额度、利率机制、期限、条件、有效期及约束范围 | 已生效合同或已到账资金 |
| 融资安排 | 当事方、接受版本、生效条件、用途及义务 | 某项目的一个银行标签 |
| 承诺与可提款空间 | 已生效承诺、占用、剩余额度、撤销和到期依据 | 可以无限重复申请的初始额度 |
| 提款批次和执行记录 | 申请、核验、批准、指令、在途、执行/失败/未知 | 全部流程只有一个 paid 布尔值 |
| 债务记录 | 本金、应计利息、费用、到期和已清偿明细 | 工程实际成本或未提款额度 |
| 监控与补救事项 | 证据、通知、条款、整改期限、决定和执行 | 私有怀疑已成为正式违约事实 |
| 银行私有认知 | 对风险、客户及市场的估计和不确定性 | 所有主体共享的真实状态 |

**BANK-003**：报价是否预留额度、预留多少及何时释放由产品规则规定。报价转合同是同一承诺的状态变化，不再额外占用一份相同承诺；并发报价与现有承诺共同检查容量。

**BANK-004**：主体的判断可能有误，核心的权限和账本校验仍必须成立。核心知道某事实，不等于银行已经获得该事实并可用于决策。

### 2.2 正式状态与私有判断的所有者

| 状态 | 银行维护什么 | 谁形成正式事实 |
|---|---|---|
| 私有风险与策略 | 客户判断、情景预测、报价偏好、误差与学习记录 | 本行认知入口更新；不得改写客户真实财务或其他银行认知 |
| 审查工作状态 | 待办、问题、材料适用范围、负责人及下一触发 | 经授权的工作提交形成任务与资源记录，意见仍有证据等级 |
| 内部批准及对外报价 | 授权范围、绑定版本、条件、有效性与撤回依据 | 核心校验后登记；不由对话文本覆盖既有报价 |
| 组合与承诺视图 | 按债务人/产品/地区等维度查询承诺、批次与债权 | 从共享正式记录派生；风险分类可以是本行判断，金额不能另算一份 |
| 监控和补救事项 | 触发事实、待核问题、已送通知、回应与待执行措施 | 核心按条款和权限提交措施，不能从内部怀疑直接改成正式违约 |
| 债务及清偿历史 | 查看本金、利息/费用组成、到期与回收 | 共同账本形成；到期清单是同一债务的视图，不新增应付 |

**BANK-022｜组合判断和最终承诺使用同一事实基线。** 风险意见记录所用 `portfolio_snapshot_ref`；实际批准/签约/执行时再读最新适用承诺和在途状态。同期其他申请已占用容量时，本次须重新校验或等待，不能凭旧快照再占一次。

### 2.3 关键对象及字段

全部对象复用 ID、来源、版本、权限、发生/生效/获知时间与业务去重标识；以下只补本角色特有字段，不设数据库实现。

| 对象 | 最小语义字段 | 状态迁移及门控 |
|---|---|---|
| 申请 `application_id` | 借款人、产品候选、用途、方案/材料版本、问题集、审查任务 | 收到 → 待补/待审 → 审查中 → 已评价；拒绝、撤回及技术待处理另列，已评价不等于批准 |
| 审查任务 `review_task_id` | 申请版本、范围、证据、负责人、投入、问题及下次触发 | 待分配 → 执行/等待资料 → 完成或按依据终止；新材料只重开受影响范围 |
| 内部批准 `approval_id` | 审查引用、签批权、金额/用途上限、条件、适用期间 | 待决定 → 批准/不批准；修改形成新版本，不自动生成客户已接受的合同 |
| 报价 `offer_id/version` | 批准引用、完整条款、可接受期间、绑定范围、预留引用 | 有效 → 被有效接受/按条款撤回/失效/被替代；终态不靠一次旧接受复活 |
| 融资安排 `loan_arrangement_id` | 双方、接受版本、额度、条件、到期表、担保及债务引用 | 已签待生效 → 生效；提款可用、受限制、未用部分关闭按范围单独表示 |
| 批次 `draw_batch_id` | 申请/批准/核实执行金额、受益人、用途、占用和执行引用 | 待核 → 批准/补充/拒绝 → 执行中 → 完成/部分/确认失败/未知；未知只能经核对消解 |
| 监控事项 `monitoring_case_id` | 条款触发、事实等级、通知、回应、责任及补救期限 | 信号 → 待核 → 无适用问题或通知/补救 → 满足并关闭/有权升级；可有独立重组分支 |
| 重组/关闭事项 | 原安排/债务组成、必要接受、调整依据、生效期、残余义务 | 提议 → 协商 → 有效调整或未达成；关闭按承诺、债务、担保、在途分别给结果 |

以下选择属于银行，正式金额、记录及状态由核心提交。收集资料、形成意见、批准、执行和到账逐步记录；既有有效授权可驱动例行操作，不要求每次重复发起模型谈判。

### BANK-A01 · 观察市场并管理融资组合

- **触发**：企业经营周期、政策/市场观察、现有客户风险或资源变化。
- **输入**：本行可见组合、到期义务、风险分布、有效政策、市场资料和融资模型边界。
- **选择**：调整新业务偏好、审查重点、可报价范围、风险调查与资源安排。
- **核心后果**：在授权范围内更新新业务策略和可执行配置；变更记录适用时间及范围。
- **等待/失败**：偏好变化不自动修改已有合同利率或撤销承诺；受约束的新政策按适用与过渡规则生效。

**函数与类型契约**

- **函数**：`roles.bank.a01(ctx: ActionContext, input: BankA01Input) -> ActionResult<BankA01Payload>`。
- **输入记录**：`BankA01Input = {portfolio_ref: Ref<FinancePortfolio>, capacity_ref: Ref<LendingCapacity>, obligation_refs: List<Ref<Obligation>>, market_refs: List<Ref<MarketObservation>>, policy_refs: List<Ref<PolicyObservation>>, strategy_space_ref: Ref<LendingStrategySpace>}`。
- **输出分支**：`BankA01Payload`：`{choice: retain_strategy / revise_strategy / investigate, basis_refs: List<Ref<Observation>>, note: string}`；调整含 `strategy_ref: Ref<LendingStrategyProfile>`；调查含 `issue_refs: List<Ref<Issue>>, scope_ref: ScopeRef`。
- **来源、接收与核心效果**：组织可见组合/政策 → 本行后续审查与经营任务；只改有权策略/任务，不回写存量条款或自动放贷。
- **分支前置与约束**：retain_strategy 不依赖新的策略候选；revise_strategy 只能选择输入允许的 profile，调查占用审查资源但不形成贷款预留。
- **业务出口与验收**：策略候选未定义返回 `unsupported`；不能越权读他行；容量竞争留待提交复核。CHECK-BANK-005/012/031/047。


### BANK-A02 · 接收申请与核对借款主体

- **触发**：收到融资申请或经授权的预先询价。
- **输入**：申请人、实际借款法人及注册/经营地、授权、项目地、用途、金额/币种、产品适用范围及披露材料。
- **选择**：进入审查、要求补充、仅给不具约束力的信息、拒绝或等待。
- **核心后果**：建立稳定申请档案和材料版本，关联申请主体与用途；身份不合格不得进入有效放款路径。
- **等待/失败**：项目尚未登记不代表所有前期询价都禁止，但融资产品需说明可接受阶段；材料缺失不自动补成合格。

**函数与类型契约**

- **函数**：`roles.bank.a02(ctx: ActionContext, input: BankA02Input) -> ActionResult<BankA02Payload>`。
- **输入记录**：`BankA02Input = {application_ref: Ref<FinanceApplication>, borrower_id: EntityId<Organization>, applicant_authority_ref: Ref<Authorization>, requested: Money, purpose_ref: Ref<FundingPurpose>, product_candidates: List<Ref<FinanceProductProfile>>, disclosure_refs: List<Ref<Evidence>>}`。
- **输出分支**：`BankA02Payload`：`{choice: accept_for_review / decline, application_ref: Ref<FinanceApplication>, finding_refs: List<Ref<EligibilityFinding>>, note: string}`；受理含 `product_ref: Ref<FinanceProductProfile>, required_condition_refs: List<Ref<Requirement>>`。
- **来源、接收与核心效果**：借款人申请/披露 → A03与借款人；受理只建审查任务，不生成贷款/报价。
- **分支前置与约束**：申请来自借款主体已提交的申请草稿，requested/purpose/borrower 必须与 application_ref 的版本一致；银行不能通过重复输入修改申请金额或法人。
- **业务出口与验收**：必要主体/用途证据缺失用 `needs_information`；明确不适用是业务拒绝；补件续用同档案。CHECK-BANK-001/017/033/043。


### BANK-A03 · 审查风险、可负担性和条件

- **触发**：资料达到可审查要求，或重要资料/项目条件发生变化。
- **输入**：获授权财务信息、需求与成本预测、偿还来源、已有债务、工程/许可风险、担保及证据质量。
- **选择**：进一步调查、形成风险意见、提出融资结构/条件、缩减额度或建议拒绝。
- **核心后果**：记录审查工作、耗时/资源、依据和不确定性；模型判断不替代正式余额及权限校验。
- **等待/失败**：多个贷款申请不能各自忽略同一借款主体已披露的已有负担；无权获知的信息保持未知而非自动读取。

**函数与类型契约**

- **函数**：`roles.bank.a03(ctx: ActionContext, input: BankA03Input) -> ActionResult<BankA03Payload>`。
- **输入记录**：`BankA03Input = {application_ref: Ref<FinanceApplication>, disclosures: List<Ref<Evidence>>, forecast_refs: List<Ref<FinancialForecast>>, debt_refs: List<Ref<Debt>>, permit_risk_refs: List<Ref<RiskObservation>>, risk_method_ref: Ref<RiskMethod>, product_ref: Ref<FinanceProductProfile>}`。
- **输出分支**：`BankA03Payload`：`{choice: recommend / conditional / decline, findings: List<BankFinding>, conditions: List<BankCondition>, assessed_amount: ValueState<BankIndicativeRange>, note: string}`。
- **来源、接收与核心效果**：有权财务/专业证据 → A04/申请人允许披露部分；只形成审查结论，不批准、承诺或提款。
- **分支前置与约束**：recommend/conditional 中需要使用的金额必须为 known 的有依据区间；decline 可用 not_applicable 且给出适用规则，不能为拒绝融资编造可贷金额。保留未知维度不等于已经满足硬条件。
- **业务出口与验收**：无风险方法 `unsupported`，未知资料不伪造成否决；条件循环明确列出负责方。CHECK-BANK-015/017/022/045。


### BANK-A04 · 批准并提出有版本的报价

- **触发**：审查结果和内部授权满足产品的报价条件。
- **输入**：本行可承担承诺、金额、期限、定价机制、费用、用途、条件及报价有效期。
- **选择**：批准并报价、附条件报价、修改、拒绝或等待。
- **核心后果**：形成唯一报价版本，明确是否具有约束力、是否预留容量和如何接受；报价金额不得绕过组合约束。
- **等待/失败**：部分批准只是部分资金额度，不推定借款方缺口已解决；报价失效或撤销按条款释放相应预留。

**函数与类型契约**

- **函数**：`roles.bank.a04(ctx: ActionContext, input: BankA04Input) -> ActionResult<BankA04Payload>`。
- **输入记录**：`BankA04Input = {application_ref: Ref<FinanceApplication>, assessment_ref: Ref<CreditAssessment>, authority_ref: Ref<Authorization>, product_ref: Ref<FinanceProductProfile>, pricing_candidates: List<Ref<PricingRule>>, capacity_snapshot_ref: Ref<LendingCapacity>, funding_path_refs: List<Ref<FundingPath>>}`。
- **输出分支**：`BankA04Payload`：`{choice: offer / conditional_offer / decline, note: string}`；报价分支含 `terms: BankTermDraft, reservation_policy_ref: Ref<ReservationPolicy>`。

### 3.2 局部类型与共同约定

各行为卡的 Input/Payload 为字段主定义；枚举列出全部业务分支，不适用字段不得携带。空列表仅表示已知没有该类项。各动作允许的提交仍须经过合同、容量与账本的正式入口；同一 A 动作可以拆成多个原子命令。

**统一分支规则。** 每个 Payload 都是由 `choice` 判别的封闭联合：共同字段每个分支都必填，只有文字明确列到该分支的专用字段才可出现；无专用字段的分支只带共同字段。Input 默认必填，`Option<T>` 的 null 仅有逐字段声明的含义；列表可为空表示已知没有，未知不能塞空列表。输出的引用必须来自获授权输入或明确已登记的准备成果，不能引用本动作尚未创建的回执、合同或任务。新内容用已定义 Draft，由核心校验后赋予正式 ID/版本。

需要有权接收方、实际选择项、付款行、执行目标或工作范围的分支，相应列表非空；空候选仅允许忽略、拒绝全部、补资料或等待等有定义的出口。金额与实际量须遵守类型、单位和正值/上限规则；note 不携带隐式价格、条件或状态。核对/恢复保留原执行身份，真实新增范围或返工另有业务任务、授权和实际投入。

### 4.2 前期咨询与有限承诺

#### 前期输入与输出的语义字段

前期咨询可关联 `owner_case_id`，不强制先创建正式项目。

| 方向 | 字段组 | 含义与使用边界 |
|---|---|---|
| 输入 | `consultation_id`、`requester_id`、`borrower_id/status` | 区分咨询人、实际借款人和借款主体尚未确定；不虚构合格法人 |
| 输入 | `owner_case_id`、`alternative_set_id`、`option_id/version` | 区分同一需要的互斥方案和可同时实施的项目，不能只按项目名称合并 |
| 输入 | `purpose`、`location_candidates`、`scale_range`、`delivery_target` | 引用业主提案；交付目标不是银行保证的完成日期 |
| 输入 | `maturity_by_dimension` | 分别记录需求、范围、专业方案、成本、工期、许可和资金计划的证据成熟度；不用单一分数抹去关键缺项 |
| 输入 | `funding_plan_version`、`cashflow_ranges`、`disclosed_obligations` | 资金来源按已持有、可支配、正式承诺、预期申请分别列示；区间含币种、价格时点、用途和时间段 |
| 输入 | `assumptions`、`evidence_refs`、`disclosure_scope` | 保留专业成本/进度意见的来源和不确定性，仅使用银行获准读取的资料 |
| 输出 | `opinion_id/version`、`basis_versions`、`as_of` | 意见绑定所审方案、财务预测及观察截止时间，后续更新保留旧版 |
| 输出 | `eligibility_view`、`indicative_structure`、`affordability_ranges` | 表达可申请性、可能结构和初步可负担性；数值若有，注明估算依据和条件，不等于实际获贷 |
| 输出 | `missing_inputs`、`condition_dependencies`、`review_triggers` | 指出缺项、由谁提供什么证据、依赖哪个决定及哪些变化需重审 |
| 输出 | `use_scope`、`validity/review_by`、`reservation_status` | 明确仅供方案比较、适用期限/重审点以及“本意见未形成融资额度预留” |

**BANK-011｜初步可负担性与正式承诺分开。** 初步意见比较各方案在有依据的成本、收入/预算与融资假设下是否可能承担，不以预测资金充当现有余额。正式报价、承诺和提款各自重新检查当时所需权限、证据、额度及执行条件；此前意见不构成批准建设。

**BANK-012｜互斥方案不重复占用整笔额度。** 比较多个备选方案只形成各自条件化结果；本行为不预留融资额度，也不将每份结果合计为可用资金。若需真正预留，另走 BANK-A04 的明确产品规则，关联共享的备选方案关系并校验本行总承诺；咨询工作实际消耗的审查资源仍照常记录。

**BANK-013｜条件依赖必须可解释。** 初步意见可依赖未来成本确认、许可、业主投入或供货条件，但须指明责任方、证据及适用节点。若“业主投入等银行承诺、银行承诺等业主投入”形成循环，列出冲突并请求改方案、补充阶段安排或按权限重新协商，不自行视作全部满足。

**BANK-014｜融资假设不自动转成产品条款。** 初步意见、非约束询价、正式报价、融资合同和已到账资金分别保存。建造方式、地区、规模、交付窗口或专业成本版本有实质变化时，重查受影响假设；既有正式报价是否失效由其条款处理，不能以新意见静默替换。

#### 可供业主比较的输出示例

同一需求有“原地扩建”和“异地新建”两个方案时，银行可分别列出预期资金峰值、可能融资覆盖、尚缺的业主投入与需要核实的证据。
两份意见使用各自的成本/工期版本；如果供货方尚未报价，相关金额只作为带来源的假设，不能写成确定的采购支出。
银行可指出异地方案涉及当前产品暂不支持的地区或用途，也可指出资料不足以判断；二者不混为已经拒绝的正式贷款。
业主仍可用这些信息调整规模、期望交付时间或候选方案，再委托专业主体补充论证；继续论证的授权与费用由业主自己的行为决定。

仍需结合 D-02/D-06 确定各类业主可使用的融资形式及前期材料最低要求；公共预算安排不自动等同于商业贷款。
咨询是否收费、免费交流是否受资源上限约束、可披露哪些预测及何时重审，分别纳入 D-03/D-04/D-09；不虚构统一收费或有效天数。

### 4.3 资金义务与执行

基础资金模型覆盖现金、应收应付、贷款与到期义务；账户、费率及融资产品须由所选模型明确。
共同定义与提交规则由[对象与状态](../02_world/domain_objects.md)中的 OBJ-011、OBJ-012 维护；本行账本视图、借款方视图与到期清单引用同一业务事实。

#### 4.3.1 业务引用与执行边界

| 语义引用 | 银行使用方式 | 禁止混用 |
|---|---|---|
| `loan_arrangement_id/version` | 引用有效融资安排、借款人、用途、承诺及条款版本 | 不以选择银行的字段代替合同 |
| `draw_batch_id`、`approval_ref` | 标识一批申请、已批准额、剩余未执行额及相关占用 | 不以 approved 表示 paid |
| `debt_id`、`debt_component` | 引用已发生的本金、应计利息或费用及其正式变动 | 不把未提款额度当成本金 |
| `obligation_id`、`due_schedule_ref` | 把到期本金/利息/费用关联同一债务组成与时间安排 | 不把贷款到期清单再加成另一笔独立应付 |
| `settlement_id`、`execution_ref` | 关联支付分配、账户、实际结果、在途及核对证据 | 重试不能创建无关联的新支付 |
| `beneficiary_id`、`trade_obligation_refs` | 区分借款人到账和直接付给供应方；后者链接被清偿的交易义务 | 实际收款人不自动变成借款人 |

以下字段定义接口语义。现金、债务、义务清偿、容量占用及事实事件遵循 OBJ-012 的一致提交，不由银行角色另写一套金额计算。
`approval_ref` 说明本次执行的权限和金额上限；支付状态说明实际结果。内部批准、批次批准和外部执行回执均保留其原本含义。

**BANK-015｜只对已核实的实际提款记本金。** 在同币种、无费用/代扣的例子中，批准 100 个货币单位而实际核实执行 60 时，本次新增本金和实际支付均为 60；其余 40 按尚未执行、执行未知或确认失败的真实分区保留，不记作已到账现金或已提款本金。净额到账或费用拆分若纳入，分别记录本金变化、各收款方现金和费用清偿，不能把净现金直接当全部本金；具体产品仍待 D-02。部分回执的新增/累计口径及去重统一遵循 OBJ-011，不由银行角色另定协议。这里的数字仅为口径示例。

**BANK-016｜未知执行不释放成可重付额度。** 对结果未知的全部或部分批次，保留对应未决占用并沿原执行标识核对。已确认部分只提交一次；未决部分不能当作确认失败、已到账或可自由再次支出的余额。

**BANK-017｜直接支付保留正确当事人。** 贷款直接支付供应商时，借款人增加实际发生的贷款债务、供应商增加实际收到的现金；借款人的可用现金不因此再增加。若同时清偿交易应付，链接原交易义务并与收款方应收同步核对，不能只写放款而漏记其清偿用途。

**BANK-018｜债务组成与到期视图不重复。** 到期清单是本金、应计利息或费用中适用部分的付款要求，不复制一笔新负债。对账汇总按基础债务及组成去重；银行债权、借款方贷款余额和到期提醒的多处展示不能叠加为总欠款。

**BANK-019｜应计、支付与核销分别记录。** 利息按生效条款及实际本金/期间计算并形成应计，支付按有效分配清偿相应组成；不自动把未付利息变成本金。银行的内部核销不代表借款方免债；确有债务减免或其他调整时，另记录权限、依据和适用金额。

提款/还款的实际发生时点、按产品确定的起息/止息或清偿生效时点，与回执核实/记录时点分别保存。迟到的可靠结果改变既往有效本金区间、清偿分配或到期状态时，按原生效条款重算受影响期间及依赖事项，以关联差额/更正事件更新现时应计、未清义务和监控依据；不能用收到回执的日期取代产品生效日。保留原应计、决定和当时可见信息，不改写过去认知；已超收部分沿共同账本形成有依据的待退款/抵扣，不能直接倒改现金。重复核对同一证据不再产生差额；生效时点/方法未知时保持核对缺口。

纯虚构方法例：本金 100，每测试时间单位 TU 按未偿本金单利 1%，付款明确仅清本金，真实清偿生效时停止计息。t=1 已清偿，可靠回执 t=3 才到；此前按本金未变暂记 [0,3) 利息 3。核实后正确应计为 1，追加关联调整 -2、当前本金为 0，保留原记录；同一回执再来新增调整为 0。该测试率和时间口径不是现实产品参数，也不选择平台时间步长。

**BANK-020｜资金不足和反向调整不得凭空补平。** 放款检查本模型中已明确的执行能力，偿还检查付款方可支配资金及授权；不足时保留未执行/未清部分，只有既有授权允许时才部分执行。更正或退回须引用原交易及实际回执/有效调整依据，保留前后记录，不删除原交易或无凭据增加现金。

#### 4.3.2 从指令到核对的正常与异常路径

1. 读取有效融资安排、该批次批准和已知执行结果，确定尚可执行的范围与收款路径。
2. 校验账户/受益人、用途、容量、相关义务及操作权限；已核实的完成部分从待执行范围扣除。
3. 按原业务标识提交执行；若存在在途或未知结果，先核对该部分，避免重复发出相同付款。
4. 核实实际发生额与币种，按 OBJ-011/012 共同规则提交现金、债务、清偿分配和占用变化，再产生观察。
5. 部分执行保留剩余；确认失败按原因处理占用与重试条件；结果未知继续核对，三种状态分别表示。
6. 到期、还款、有效减免、退款或更正都回到原债务/义务/交易引用，保留追踪链。

对于同币种且无费用/代扣的简单示例，银行直接向供应商支付 60，借款人新增本金 60；若这是指定交易义务的有效支付，该义务已清偿部分也为 60。
供应商应收减少、实际现金增加，借款人交易应付减少；借款人贷款余额与交易应付分别反映新融资和原交易，不把放款额追加为第二份交易应付。
跨币种金额如何转换尚待确定，不能把不同币种直接相加，也不能静默套用汇率或税项来补齐示例。

### 4.4 大湾区融资与资金路径

大湾区是本模型的研究范围，不是统一授信、币种或支付制度的假设。以下定义银行需要核验的接口；不预选现实银行产品、利率、币种或跨境规则，也不以组织地区标签替代业务资格。

**BANK-029｜贷款适用性由主体、地点、用途和产品共同决定。** 银行组织/获授权服务单位的注册与经营范围、实际借款主体身份、项目地、资金用途、账户及收款方位置分别记录。某行在研究范围内出现，不表示它能向全部地区、全部主体或全部项目报价；产品不适用、事实未知和银行商业拒绝是不同结果。

| 语义输入 | 最小引用/状态 | 不能推定 |
|---|---|---|
| 银行与授权单位 | 组织、经办授权、注册地/服务地区、有效期间与来源 | 相同 Bank 角色共享授信权限或可互换服务资格 |
| 借款责任主体 | `borrower_organization_id`、注册/经营地、授权、关联项目或用途 | 项目参与者、实际收款人、担保人与借款人为同一主体 |
| 产品与地域适用性 | `product_id/version`、借款人类别、项目地/用途、允许资金路径、依据来源和生效/过渡范围 | 大湾区共用同一产品、同一额度或同一适用条件 |
| 金额与币种 | 报价、承诺、批准、实际执行、债务与到期义务各自的币种及金额 | 无换算依据直接相加，或默认不同账户的数额可一比一转移 |
| 执行路径 | 借款方到账/直接付款、付款与收款账户或主体、执行授权和共同结算标识 | 授信批准已满足账户、资金、收款资格或执行路径条件 |
| 组合边界 | 本行承诺/执行能力、同一借款组织的项目与债务、可见担保及限制 | 每个项目各获得一份组织初始现金/额度，或集团成员自动互相担保 |

**BANK-030｜授信容量与可执行资金分别核对。** 银行在 A03—A06 判断能否承诺、报价和批准批次，在 A07 执行前仍核对适用资金模型中的实际执行能力。承诺不足、执行资金不足、路径不支持和条件不满足分别记原因。某币种有剩余额度不自动补足另一币种的现金缺口；使用何种资金来源、准备金或清算抽象仍需 D-02 明确，不能擅自用贷款本金生成规则填补空缺。

未启用兑换机制时，不生成虚构汇率、兑换现金或结算成功。若所选模型只支持选定币种/路径，应把范围写入产品和场景，对超范围请求返回明确不支持或待补充；不得静默改币种、改变收款方或换一个已选产品。报告币种的估值折算也不等于发生兑换或还款。

| 行为节点 | 输入与本行决定 | 正式后果 | 拒绝/等待路径 |
|---|---|---|---|
| A13 前期融资咨询 | 需要与方案成熟度、候选地区/用途、借款组织、资金假设；可出条件化意见或指出资料缺项 | 有版本、适用范围及假设的咨询记录；不保兑资金、不预占每个互斥方案的全额额度 | 未知资格/账户可列后续核验，不把可咨询等同可承诺 |
| A02/A03 受理与风险判断 | 产品范围、主体授权、项目资料和已披露多项目负担；可受理、补充、缩额、拒绝或等待 | 申请、审查记录及缺项明确；不把获知他行融资的请求当作可直接读取他行私有账本 | 适用性未知与材料不足可等待；不适用按依据解释，不自动转交有权主体之外的全部材料 |
| A04/A05 报价与安排 | 本行当前组合、产品/条款版本和对方同版接受；决定报价、变更或确认安排 | 有效报价/承诺/安排分别登记，同一预留只转移一次；尚无实际贷款到账 | 失效、拒绝、改址或改产品触发相应重审；未签新安排不删除原有义务 |
| A06/A07 批次与执行 | 当前可用空间、逐批条件、币种、资金路径及唯一执行标识；批准范围与执行指令分别授权 | 实际回执驱动 OBJ-011/012：到账路径记借款方收款；直接支付记实际收款方收款与借款方相应债务 | 部分完成只记实际结果；未知部分保留占用并先核对，禁止因超时整批再付 |

**BANK-031｜跨项目判断按实际责任主体与可见信息汇总。** 本行承诺、已批准未执行和未知在途占用使用统一来源核对；同一业主多个项目竞争其真实资金与偿还能力。项目级限额、组织级限额或已启用担保可以同时存在，但引用同一风险/义务范围以避免重复计量。银行只使用获授权披露的外部负担；核心按共同约束校验正式提交，不把核心掌握的全部他行资料反向泄露给本行。

**BANK-032｜政策影响商业判断，不能代替融资事实。** 政策记录保留发布主体、适用地区/主体/用途、版本、有效与过渡条件及本行获知时点。政策鼓励可影响可选产品、需求或风险预期；补贴承诺、担保和实际资金只有经过相应有权流程才成为可引用事实。政策变化是否影响已有报价或安排依适用条款判定，不默认追溯改写合同、不保证所有申请获贷。

跨地区金额提交、部分回执、未知执行、冲销和费用拆分沿用资金接口与共同账本，不另造地区专属的第二份债务。跨地区交易若未建模应留在明确研究边界内；可行、不适用、未知和模型未支持四种结果须可区分。

## 5. 状态转换、失败与恢复

### 5.1 提交、版本与持续约束

**BANK-005**：同一融资安排的初始承诺、有效调整、已占用提款、撤销/失效及剩余额度能核对。批准未执行、执行中和已执行批次不能互相遗漏，也不能重复占用。

**BANK-006**：非循环产品中，还本不默认恢复可提款额度；循环产品按明确条款恢复。具体定义应与 D-02 选择的产品一致，不混用两种算法。

**BANK-007**：实际提款产生的债务与资金路径一致；本金减少须对应清偿或有效调整，利息/费用的支付单独记录。工程成本中是否纳入融资费用须声明汇总口径，避免重复计入。

**BANK-008**：条款条件具有类型、范围、责任方、证据、满足状态和期限；“提交报告”“按里程碑提款”这样的文本本身不代表已有可执行核验。

**BANK-009**：合同、银行选择、双方参与关系、金额承诺、批次及事件采用共同的一致提交边界。银行 generic 角色资源占用不替代货币承诺。

**BANK-010**：技术执行未知、业务资料不足、权限拒绝和违约是不同结果。重试沿业务标识核对已有提交，不通过重试制造重复贷款或重复收款。

### 5.2 对象转换与剩余责任

**BANK-025｜监控信号、违约和恢复分别有门槛。** 工程延期、报表缺失和资金缺口先形成适用问题；是否违约、需何种通知/补救以及如何恢复按有效条款确认。满足补救后恢复对应权限须有证据和有效措施，不能只降低风险分或收到一句承诺就重开全部提款。

**BANK-026｜重组承接债务而不制造清偿。** 延期、调整支付安排或减免按所需有效接受和权限生效，关联原债务组成与调整记录。重组尚在谈判时原义务继续适用，除非有另行有效暂缓依据；修改到期表不记录现金回收，也不把承接余额再加成第二份贷款。

**BANK-027｜关闭是多对象核对。** 未用承诺到期可按条款关闭，但已提款本金、应计费用、担保和未决执行继续保留各自状态。只有所需条件分别满足，才能把整个安排标为收尾完成；运行截止只形成未结清单。

### 5.3 等待、续办与版本接续

等待保存阻塞原因、责任接口、下一触发或复核时点，不能把无输出当作处理完成。

**BANK-023｜补件与报价更新保持身份连续。** 申请补件以问题 ID 关联原档案，保留未受影响审查；形成新报价则明确新旧版本关系。接受与到期同一时点发生时，按已选时间/事件规则核验报价效力，不因处理先后偶然复活过期报价。

**BANK-024｜等待占用有具体对象。** 审查人员、报价预留、提款未决占用及债权不是同一种资源。资料待补期间是否保留人员按任务规则处理；资金执行未知保留相应未决占用，不能为释放审查人员顺带消除债务或付款占用。

待办至少记录 `blocked_by`、`responsible_party`、`next_trigger` 和适用的 `review_at`；外部补件、容量释放、有效期到达和技术恢复分别触发相应续办。
若任务因技术原因没有结果，保留最后已提交状态及仍适用的业务时钟；不能将一次模型重试当作新的金融申请，也不能无依据重置报价期限。
重排人员只改变任务安排；款项、承诺和债务的改变仍需各自有效业务依据，保证本行经营排期与财务事实可分别核对。

### 5.4 正常路径与失败恢复

**情境一：多个申请竞争有限能力，其中一项正常履约。** 下列顺序只是示例，不指定首批产品或期限。

1. 银行收到两个独立借款人的申请，在同一组合基线上识别共同风险及审查资源需求，可先要求其中一个补充材料。
2. 已有充分依据的申请经审查进入签批；正式提交读取最新容量，形成有明确期限及预留规则的报价。
3. 借款人有效接受同一版本，报价预留按规则转为安排承诺；另一申请不能继续使用转出前的空余额。
4. 条件逐项满足，首个提款批次核验后实际执行，第二批仍可因里程碑证据不足等待；不让一次通过覆盖所有批次。
5. 存续期依条款观察、应计及核对回款；到期清单引用已有债务，偿还按有效次序清偿组成。
6. 未用额、全部债务及必要附属义务分别收尾，银行再基于当时可见的预测误差更新下一轮判断。

**情境二：补件期间报价失效。** 银行要求更新成本证据，记录所影响的风险和金额假设；原报价按自己的效力规则运行。
借款人提交旧报价接受时，若已失效就说明失配并要求重新报价/接受，不把补件当作自动续期。
银行对新资料复核并重新校验组合容量后可以重报，也可以不报；此前有效的其他审查记录和已经发生的工作成本保留。

**情境三：发生偿还困难后达成重组并恢复。** 到期少付留下实际未清金额，银行核对适用违约及通知条件，先形成可追踪事项。
借款人提出重组不自动改变债务；双方必要决定生效后，调整原安排的相应组成和到期计划，记录仍存的费用、担保或限制。
若恢复提款需满足额外条件，按该恢复依据逐项核对；如重组未达成，继续依原有效条款或另有依据的补救措施处理。

**情境四：最后一笔执行未知且额度已到期。** 先核对原交易；可关闭的未用部分按条款收尾，未知部分不重新支付也不凭空销账。
核实成功就一次性登记实际债务与支付；核实未发生则按到期安排判断是否仍可执行，不能因曾经批准而忽略后续效力条件。

### 5.5 收尾、观察与经营反馈

**BANK-028｜评价沿自身可见业务结果。** 分别观察申请处理、报价接受、执行及时性、逾期、实际回收与预测误差，并标明样本、时间及未成熟结果。高接受率不自动等于稳健，重组成功不自动等于全部收回；参数学习是否启用仍按研究配置，不以事后结果改写过去记录。

## 7. 参数、方法与配置依赖

大湾区融资规则按借款主体、项目地、业务单位、产品与执行路径选择。现实依据记录发布机构、适用范围、版本和有效时点；研究抽象与未建模内容另列，不能将单一地区产品类推为湾区统一规则。

- **资金与产品（D-02/D-06）**：账户结构、融资产品、容量、风险维度/阈值、利率/费用、币种转换和执行精度；各类业主的融资形式及前期材料最低要求。公共预算不自动等同于商业贷款。自有资金及单银行非循环产品仅为候选基准，产品组合须显式选择。
- **任务与竞争（D-03—D-05）**：咨询收费与免费交流边界、审查投入、计息和处理时钟、并发承诺分配及资源上限。
- **信息与收尾（D-09/D-10）**：预测披露、调查权限、重审条件、违约处置和学习算法。高级会计、税务、外汇及完整银行机制未明确时保持未覆盖。

未选定的方法、阈值、时间粒度、资格和产品条件须显式保持待定；不得以示例值、角色标签或未覆盖范围补成正式结论。具体选择登记在[模型决策](../07_experiments/model_decisions.md)，使用前绑定方法、数据和参数版本。
